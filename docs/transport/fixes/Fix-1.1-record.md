## Behaviour change

A POST `/transport/book` with the same `idempotency_key` and the same
authenticated user now yields exactly one `Booking` row; replays return
the first booking's `booking_reference` with `idempotent_replay=True`.
A concurrent submit loses the unique-index race, is caught by the
`IntegrityError` handler, and is converted into a replay instead of a
`ServiceUnavailableError`.

## Agent-behaviour note (learned during this fix)

When a Fix-1.1 test failed, the root cause was **not** in the service:
`BookingService` was contract-compliant. The failure came from
**test-state leakage**: `_isolate_db` (conftest) skips auto-cleanup for
`@pytest.mark.threaded` tests, the repo convention is that threaded
tests self-clean every row they create (see
`tests/test_transport_concurrent_claim.py _delete`), and the shared
`ix_booking_idem` index is global on `idempotency_key` (contract
Section 5), so a leaked keyed row from one run collided with a fresh
`test_user` on the next run.

**Rule:** On a test failure, the agent must first state which Scope-In
file is the cause; otherwise the cause is scaffolding (shared fixtures,
DB state, conftest) and is only fixable via the fix's own test file —
never by editing shared fixtures.
